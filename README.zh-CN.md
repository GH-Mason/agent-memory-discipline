# LLM Agent 的记忆纪律

*该写什么、纠正时怎么改、留多少、以及如何清理一个长期运行 agent 的记忆而不丢关键信息。*

大多数 agent 记忆项目都在解决**架构**问题：向量库、图记忆、检索管线、更大的上下文窗口。这个仓库讲的是另一半——**纪律**。它记录一个长期运行的个人 agent 实际遵循的操作规则，以及一次证明"有些规则不能省"的事故复盘。

规则来自把两本经典文本映射到 agent 的日常行为上：

| 来源 | 借用的概念 |
|---|---|
| **《工程控制论》**——钱学森（1954） | 反馈伺服 · 多变量系统的解耦控制 · 观测噪声的滤波 · 自寻最优控制 · 自适应控制 · 冗余与容错 |
| **《系统之美》**——德内拉·梅多斯（2008） | 存量与流量 · 韧性 · 杠杆点 · 有限理性 |

> 本仓库分享的是**我们的实践笔记**，不是书的原文——见[来源](#来源)。

## 所有人都会踩的失效模式

agent 的长期记忆是一笔**只有流入、没有自然流出的存量**。每次写入都很便宜，也没有东西会自动过期。默认会走向：

- **堆叠发散。** 用户纠正了一个事实，agent 在旧条目**旁边**新增一条。两条互相矛盾的记录并存，未来的检索变成抛硬币。
- **容量膨胀。** 预算写满了，直觉是加大预算。召回反而**变差**——同样的注意力被摊薄到更多、更弱的信号上。
- **无人看管的清理。** 维护任务裁掉"过时"条目，顺手删掉了承重规则。我们真发生过。→ [docs/failure-modes.md](docs/failure-modes.md)

下面五条原则就是解药。

## 五条原则

### 一、闭合反馈回路——改旧，不增新

> 工程控制论：伺服系统把输出与期望比较、得出误差、用误差修正。它**不会**在原输出旁边再加一个输出。

用户纠正已存事实时，**重写**那条条目：

- `replace` 旧条目（或 `remove` 掉它）——绝不用 `add` 追加一个"纠正版"
- 同一事实出现两条 = **发散**，不是冗余
- 每次纠正后验证：旧条目已消失、新条目在位、有且只有一份

### 二、解耦——存储分离、领域隔离

> 工程控制论：多变量系统里，每条控制通道的动作不应干扰其他通道。

写入前先判断这条信息**该进哪个 store**：

| 信息类型 | 去处 |
|---|---|
| 用户稳定偏好、身份、反复出现的纠正 | 用户档案 |
| 环境事实、惯例、教训、工具坑 | agent 工作记忆 |
| 可复用流程、清单、工作流 | **技能/文档**——绝不进事实记忆 |
| 任务进度、编号、一次性结果 | **哪都不存**——从会话历史重建 |

领域（工作 / 生活 / 财务 / 通信）分开记；一条目只写一件事。

### 三、滤波——记忆留给"稳定"，不留给"最近"

> 工程控制论：在带噪观测中滤波，保留真正重要信号的最小均方估计。

容量有限，滤波不是可选项。命中以下任一条即拒收：

- 几天内就过时的（日期、进度、单号、临时状态）
- 搜一次就能再查到的（API 细节、文档摘录）
- 未核实、低信任的说法——先核实再存
- 情绪话、一次性对话内容

每次写入前自问：*这条消失了，我会真的付出代价吗？* 不会，就是噪声。

### 四、自适应——预算固定，定期压缩

> 工程控制论（自寻最优、自适应控制）：系统测量自身，在约束内向更优工作点修正。

- 定明确的字符预算。**不要靠扩容解决增长**——压缩、合并。
- 占用率保持在高信号区间；太宽松的记忆会稀释召回。
- 按周期跑自动巡检；每次产出人可读报告；无事发生时静默。
- 占用越过触发阈值时向目标值压缩——给第二天的写入留余量。规范数字只维护在 [docs/operations.md](docs/operations.md) §1–4 一处。

### 五、冗余——文件是真相源

> 工程控制论：冗余与容错让单个组件失效不至于拖垮整个系统。

- 承重约定放**两处**（例如每轮注入的记忆 + 规则文件），丢一处仍可运行。
- 长文本放文件；记忆里只留**指针**。
- 带日期的具名文件让每个产物可检索——可观测性也是一种命名纪律。

## 三条内核检查

大多数记忆 bug 不是架构问题，而是回路问题：

| 检查 | 防的失效 | 做法 |
|---|---|---|
| **收敛性**（稳定性） | *振荡*——纠正一次，下周又悄悄变回去 | 每次重写后验证旧去新来；同一主题若需纠正**第二次**，定位根因（匹配失配？放错 store？）一次改干净 |
| **防抖**（扰动抑制） | *噪声入库*——一句随口吐槽变成永久政策 | 拿不准是否稳定？等它第二次出现再落 |
| **能观性** | *死存储*——存了却永远检索不到 | 每轮注入的记忆 = 强观测；文件 = 弱观测，必须由记忆留指针，否则等于没存 |

```
  operations.md            数字、写入流程、清理回路、护栏设计
  porting.md               各框架安装配方（Claude Code / Codex / Cursor / 通用）
  failure-modes.md         反模式 + 事故复盘（已脱敏）
templates/
  injected-rules.md        粘进规则层的常驻短块
  MEMORY.template.md       工作记忆模板
  USER.template.md         用户档案模板
  cleanup-checklist.md     人可读的巡检清单
scripts/
  memory-audit.py          占用率 + 候选清单报告（纯 stdlib，只读）
  cleanup-preflight.py     故障保险：清理运行前检查 procedure/skill 完好
  memory-verify.py         验证一次编辑：预期改动落实、无其他变动
  check-example.py         文档即测试：文档引用输出 == 真实输出
examples/
  example-memory.md        合成样例存储
  README.md                样例审计输出 + 各标记含义
skills/
  control-theory-memory/   写入时规则（Hermes skill 格式）
  memory-hygiene/          清理时规则（Hermes skill 格式）
```

`skills/` 两个文件是 Hermes skill 格式；规则本身与框架无关——搬到你 agent 每轮注入的规则层即可。

## 快速上手

1. 先找到你的两个安装点，照 [docs/porting.md](docs/porting.md) 里对应框架的配方走（Claude Code / Codex / Cursor / 通用）。
2. 把 [templates/injected-rules.md](templates/injected-rules.md) 粘进 agent 每轮都能看到的层。没被注入的规则等于没有。
3. 复制两个 store 模板、设定字符预算，用 `python3 scripts/memory-audit.py <你的>/MEMORY.md` 看占用——示例输出见 [examples/](examples/README.md)。
4. 排上清理回路（每晚或每周）——但必须带上 [docs/operations.md](docs/operations.md) 里的护栏；头一个月记录每次删了什么。每次运行先跑 `scripts/cleanup-preflight.py`，并在动手前给 store 做快照。
5. 把四个[失效演练](docs/operations.md)各跑一次。成本很低，而且这是唯一能证明护栏真实有效的办法——尤其是 protect-list 演练，它就是事故的现场复现。

## 状态与结论上限

这是 **n = 1 的实地笔记**，不是对照实验：

- 来自一个长期运行的个人助理的真实使用经验（数月日常运行）
- "60–70% 密度"是**经验观察**，不是实测定律
- 事故按实际发生记录，不是实验设计
- 把里面的数字当**待调的起点**，别当默认值信

## 相关项目

架构优先的项目——[MemGPT/Letta](https://github.com/letta-ai/letta)、[Mem0](https://github.com/mem0ai/mem0)、[Zep](https://github.com/getzep/zep)——解决的是**存储**本身：检索、压缩、分层。本仓库是互补而非竞争：它是你**任何存储之上**的**运行纪律**——什么该写、纠正怎么落、清理怎么跑而不至于悄悄删掉保护它的规则。即使你的记忆跑在这些系统里，这套规则依然作用于写入那一层。
